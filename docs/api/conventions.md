# API conventions

Applies to every endpoint. Example implementation: `src/modules/sample/`.

## URLs and versioning

- Everything is under `/api`, with the major version in the path: `/api/v1/orders`.
- Resources are plural nouns in kebab-case: `/api/v1/order-items/{id}`. No verbs in paths;
  use sub-resources or a POST on an action resource only when CRUD does not fit
  (`POST /api/v1/orders/{id}/cancellation`).
- Methods: `GET` read, `POST` create (201 + body), `PATCH` partial update, `PUT` full replace,
  `DELETE` (204). Do not use `GET` to change state.
- A new major API version (`/api/v2`) is a breaking change for the whole module; prefer
  additive changes within v1.
- Probes (`/health/live`, `/health/ready`) are outside `/api` and not versioned.

## Requests and responses

- JSON, `camelCase` fields. Every body, query and response has a Zod schema (DTO).
- Unknown request fields are stripped. Response schemas list exactly what clients get.
- Never return entities directly; map them (`toXxxResponse`).
- `x-request-id`: clients may send one (8–128 chars of `A-Za-z0-9._:-`); the response
  always contains it. Quote it in bug reports.

## Data types

| Kind            | Format                                                                                                   |
| --------------- | -------------------------------------------------------------------------------------------------------- |
| Ids             | UUIDv7 strings, generated by the server (`newId()`).                                                     |
| Dates and times | ISO-8601 in UTC with `Z`: `2026-01-31T12:00:00.000Z`. Dates without time: `YYYY-MM-DD`.                  |
| Money           | Integer minor units plus ISO 4217 currency: `{ "amount": 1999, "currency": "EUR" }`. Never floats.       |
| Enums           | Lower-case strings (`"processed"`). Adding a value is a breaking change for strict clients: announce it. |
| Optional values | Omit the field in requests; in responses use `null` for "no value".                                      |

## Pagination

Cursor-based for every list:

- Query: `limit` (1–100, default 20) and `cursor` (opaque, from the previous page).
- Response: `{ "items": [...], "nextCursor": "..." | null }`.
- Order is stable and documented (default: newest first by `createdAt`, then `id`).
- Clients must treat cursors as opaque strings. An invalid cursor answers 400.

## Errors

All errors are [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) Problem Details,
`Content-Type: application/problem+json`:

```json
{
  "type": "urn:problem-type:sample-not-found",
  "title": "Not Found",
  "status": 404,
  "detail": "The sample was not found.",
  "instance": "/api/v1/samples/0197...",
  "code": "SAMPLE_NOT_FOUND",
  "requestId": "01a1..."
}
```

- `code` is stable and machine-readable (`UPPER_SNAKE_CASE`); clients switch on it, never on
  `detail`. Changing a code is a breaking change.
- Validation errors (400, `VALIDATION_FAILED`) add `errors: [{ path, message, code }]`.
- Retryable errors add `"retryable": true` (for example `CONCURRENT_UPDATE`, `QUERY_TIMEOUT`).

| Status | When                                                       | Typical codes                                                                     |
| ------ | ---------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 400    | Invalid input                                              | `VALIDATION_FAILED`, `BAD_REQUEST`                                                |
| 401    | Missing/invalid/expired token (`WWW-Authenticate: Bearer`) | `UNAUTHORIZED`, `INVALID_TOKEN`, `TOKEN_EXPIRED`                                  |
| 403    | Authenticated but not allowed                              | `FORBIDDEN`                                                                       |
| 404    | Not found, or not visible to the caller                    | `<RESOURCE>_NOT_FOUND`, `ROUTE_NOT_FOUND`                                         |
| 409    | Conflict with current state                                | `VERSION_CONFLICT`, `UNIQUE_VIOLATION`, `REFERENCE_CONFLICT`, `CONCURRENT_UPDATE` |
| 413    | Body too large                                             | `PAYLOAD_TOO_LARGE`                                                               |
| 422    | Breaks a business or database constraint                   | `CONSTRAINT_VIOLATION`                                                            |
| 500    | Unexpected error (details only in logs)                    | `INTERNAL_ERROR`                                                                  |
| 503    | Dependency unavailable                                     | `AUTH_UNAVAILABLE`, `QUERY_TIMEOUT`                                               |

Services throw domain errors (`src/core/errors`); the global filter builds the response.

## Authentication and authorization

- Bearer JWT from the OIDC provider on every endpoint unless marked `@Public()` (with a
  comment saying why).
- Roles (`@Roles(...)`) are a coarse first check. Services check access to each resource
  (ownership, tenant, state). Resources the caller may not see answer 404; actions not
  allowed on a visible resource answer 403.

## Concurrency

Updates of shared resources send the `rowVersion` they read. A stale version answers
409 `VERSION_CONFLICT`; the client reloads and retries.

## Contract and versioning

- `openapi/openapi.json` is generated from the code (`pnpm openapi:generate`) and committed;
  `pnpm verify` fails if it is stale.
- The `contract/` package (`{{NPM_SCOPE}}/api-contract`) publishes it with TypeScript types.
  Its version is SemVer and is the document's `info.version`:
  breaking change → major, new optional field or endpoint → minor, docs only → patch.
- Breaking changes need a CHANGELOG entry starting with **BREAKING:**.
